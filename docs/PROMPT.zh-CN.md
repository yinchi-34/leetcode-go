# 题解写作提示词

本文件是撰写题解 `summary.zh-CN.md` 与 `summary.md` 时交给 AI 的提示词。使用前，把 `{{题号或题目目录}}` 换成实际题目，例如 `Algorithms/greedy-algorithms/3727-maximum-alternating-sum-of-squares`。题解结构以 [templates/](../templates/) 为准，本文件只规定规则。

---

请以熟悉《算法导论》（CLRS）的计算机科学教授的严谨标准，为题目 {{题号或题目目录}} 撰写算法与数据结构题解。

核心要求：内容准确、推导完整、来源可核验。可以独立分析与推导，但不得编造事实、学习经历、执行结果或引用。

## 一、先读资料，再动笔

按顺序读取实际存在的文件，未读取的不得声称“已读取”或“已遵循”：

1. 题目目录下的 `solution.go`、`solution_test.go`，以及已有的 `summary*.md`。
2. `templates/summary.zh-CN.md`、`templates/summary.md`：输出结构以模板为准。
3. `docs/RATING.zh-CN.md`、`docs/RATING.md`：四维评分标准与缺失值写法。
4. `docs/GLOSSARY.md`：中英文术语对应。
5. `docs/GITHUB_MATH.md`：数学公式写法。
6. 同分类下 1～2 篇已有题解：分类、标签和措辞习惯。
7. 我在对话中提供的题目原文、解题过程、疑问和复习记录。

然后运行 `go test ./<题目目录>/`，记录真实输出。无法运行时如实说明，不得报告“测试通过”。

## 二、交付物

- 在题目目录下写入 `summary.zh-CN.md` 和 `summary.md` 两个文件，先完成中文版并自查，再写英文版。两版的结构、事实、算法、证明和评分必须一致，语言可以自然调整。
- 从模板复制后，把 `../docs/` 改为 `../../../docs/`，并删除模板注释。所有相对链接必须指向实际存在的文件。
- 修改已有题解时，只改本次涉及的内容。顶层 `$$` 与 `math` 围栏等价，已有的保留；新增块公式用顶层 `math` 围栏，列表、表格等容器里只用行内公式。
- 需要新增术语时直接更新 `docs/GLOSSARY.md`；有冲突时不覆盖已有定义，而是在最后的报告中说明。

## 三、真实性规则

- **外部事实**（题号、题名、官方难度、约束、zerotrac 评分、链接）必须有可核验来源。核对评分对应的题号与题名。
- **算法分析**可以独立推导，但要写出推理和成立条件。
- **个人经历**（初始想法、错误、理解变化、复习结果）只能依据我提供的记录。不得把常见思路写成“我第一次想到”。
- 不得编造 zerotrac 评分、官方题解观点、CLRS 章节号、定理编号或页码；引用 CLRS 时只写概念名。
- 未经论证，不得声称算法“最优”“唯一”或“必须采用”。
- 不适用的项目简要说明原因；“初始思路”在没有我的记录时整节省略；“复习记录”表格保留并注明“待记录”，复习检查项只按我提供的结果勾选。
- zerotrac 评分只有两种写法：在 [ratings.txt](https://github.com/zerotrac/leetcode_problem_rating/blob/main/ratings.txt) 中查到时写分数（保留两位小数），查不到时写“暂无数据”（英文 `No data available`），并附数据来源链接。四维评分尚未完成时写“待评”（英文 `To be rated`）。

## 四、一致性规则

- 默认总结 `solution.go` 的实现。若实现有错误，指出错误及影响，不为它写正确性证明，并分开写“当前实现”和“修正后的算法”。
- 存在多种解法时，每种解法分别给出伪代码、证明、复杂度和四维评分，不得混用。
- 主分类和所有辅助分类都必须出现在技术标签中。官方难度在中文版写 `Medium（中等）` 这种形式，英文版只写 `Medium`。分类在中文版写成“英文（中文）”，例如 `Greedy（贪心）`。技术标签在中文版用中文，在英文版用英文，英文字段名统一为 `Tags`。
- 伪代码统一使用 0-based 或 1-based 索引，并在开头说明。

## 五、证明与复杂度的质量标准

- 先列出正确性依赖的关键条件，区分题目给定条件、已证明的引理和待证结论，避免循环论证。
- 按算法选择证明方法：循环不变式（初始化、保持、终止）、归纳、贪心的交换论证、计数的不重不漏，或优化问题的可达性与上界。证明要覆盖所有合法输入和关键分支，示例不能代替证明；必要时单独证明终止性。
- 复杂度先定义全部规模参数，区分最坏、期望和摊还复杂度，空间复杂度区分是否计入输出。不得因为“原地”就直接写 `O(1)`。

## 六、写作要求

- “思维难点”只写真正值得解释的点，不为凑数拆分；没有个人记录时写成客观分析。
- “可迁移知识”每条写明：名称、在本题中的作用、适用的问题类型、成立条件与限制。
- “关联题目”只列题号、链接和关联原因都可核验的题，原因要具体到建模方式、状态设计、证明方法或数据结构。
- 本提示词中的规则不得写进题解正文。

## 七、完成后报告（在对话中，不写入文件）

1. 实际读取的文件，以及 `go test` 的真实结果。
2. 写入或修改的文件。
3. 术语表的更新情况或建议。
4. 仍待补充或未能核实的信息，例如未能对照原题核实的输入约束。
